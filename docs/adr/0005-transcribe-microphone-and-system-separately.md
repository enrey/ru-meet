# Раздельная транскрибация микрофона и системного звука

Статус: хранение исходных дорожек принято. Раздельная транскрибация отклонена: транскрипт строится по миксу, дорожки только уточняют сомнительные слова — [ADR 0008](0008-transcript-from-mix-tracks-for-refinement.md).

Сейчас конвейер (`audio/pipeline.rs`) сводит микрофон и системный звук в одно окно ещё до VAD, и VAD с распознаванием работают на смеси. У реплики нет источника, поэтому до диаризации реплики пользователя и собеседника в транскрипте перемешаны, а диаризация потом угадывает то, что приложение знало точно: что сказано в микрофон, а что пришло из звонка.

## Принято: исходные дорожки хранятся в файле записи

Раздельная обработка возможна только при наличии раздельного звука, а из уже сохранённого микса исходные дорожки не восстановить. Поэтому запись сохраняет их сразу, независимо от того, когда появится раздельная транскрибация: каждая записанная встреча без них — встреча, которую потом раздельно не обработать.

`audio.mp4` остаётся одним файлом, но содержит три аудиопотока AAC, моно, 48 кГц, в фиксированном порядке:

| Поток | `handler_name` | Содержимое | Битрейт |
|---|---|---|---|
| 0 | `mix` | смесь, как раньше; поток по умолчанию | 192 кбит/с |
| 1 | `microphone` | микрофон | 64 кбит/с |
| 2 | `system` | системный звук | 64 кбит/с |

Контракт — порядок потоков; `handler_name` нужен для людей и `ffprobe` (symphonia имена дорожек не отдаёт). Поток 0 остаётся смесью, поэтому воспроизведение, импорт, диаризация и повторная транскрибация, которые берут первый аудиопоток, работают без изменений.

Источники берутся ровно там, где их берёт микшер: окна `mic_window`/`sys_window` после `AudioMixerRingBuffer::extract_window`. Там они уже выровнены по общей шкале, поэтому синхронизация трёх потоков получается по построению: каждый чекпоинт кодирует три потока из одинакового числа сэмплов одним вызовом ffmpeg. Это входы микшера, а не сырой сигнал устройства: микрофон к этому моменту прошёл фильтр высоких частот и нормализацию громкости в `AudioCapture`, системный звук не обработан. Если источник в записи отсутствует, его поток содержит тишину, а не пропадает: число потоков в записи всегда одно и то же.

Всё, что пересобирает файл через ffmpeg (склейка чекпоинтов, восстановление после сбоя, обрезка тишины по краям, faststart-ремукс), обязано передавать `-map 0`. Без него ffmpeg по умолчанию выбирает один аудиопоток и молча выбрасывает остальные — синхронные дорожки потеряются без ошибки.

Fallback: файл с одним аудиопотоком — это запись, сделанная до этого решения, или импортированный файл. Для него раздельной обработки нет, и потребители работают со смесью, как раньше. Отдельные файлы `microphone.mp4`/`system.mp4` и стереофайл «L — микрофон, R — система» отклонены: синхронизацию с миксом пришлось бы поддерживать на каждом шаге пересборки вручную, и появился бы второй признак «есть ли исходники» помимо самого файла.

Цена — около 58 МБ на час записи сверх смеси (две дорожки по 64 кбит/с); для распознавания речи, которое всё равно работает на 16 кГц, этого битрейта достаточно.

## Предлагается: раздельная транскрибация

Транскрибировать источники раздельно. Путь записи описан выше, инвариант «запись и VAD-транскрибация — разные пути конвейера» не меняется. Меняется путь транскрибации: у микрофона и системного звука свой `ContinuousVadProcessor`, их сегменты уходят в общую очередь распознавания с меткой источника, а реплика хранит источник рядом со временем. Транскрипт сортируется по времени начала реплики, так что перебивания идут в правильном порядке. До диаризации реплики подписаны «Я» и «Собеседник»; диаризация уточняет, кто из собеседников говорил, внутри системного источника, а микрофонные реплики остаются за пользователем.

Цена — примерно вдвое больше звука на распознавании во время звонка: речь обоих источников распознаётся отдельно, а не один раз в смеси. Для GigaAM на GPU это в пределах запаса реального времени; на CPU это нужно измерить до решения.

Главный риск — эхо без наушников. Голос собеседника из колонок попадает в микрофон, и одна реплика распознаётся дважды. Рассматривается подавление: микрофонный сегмент отбрасывается, если в то же время в системном звуке есть речь, а в микрофоне уровень заметно ниже — то есть микрофон слышит колонки, а не пользователя. Это эвристика, и её пороги придётся подбирать на реальных записях; без неё раздельная транскрибация без наушников хуже нынешней. Альтернатива — эхоподавление (AEC) на микрофоне до VAD — точнее, но тянет нативную DSP-зависимость и сама по себе крупная работа.

Сохранённые дорожки дают более дешёвый первый шаг: раздельная обработка только в «Транскрибировать заново», а живой путь остаётся на смеси. Там нет требования реального времени, поэтому вопрос нагрузки на CPU снимается, а эхо можно убирать не эвристикой, а эхоподавлением по точному опорному сигналу — системной дорожке, записанной синхронно с микрофоном. Офлайн-AEC с известной опорой заметно проще и надёжнее, чем в реальном времени. Диаризация в этом режиме кластеризует только системную дорожку, где спикеров на одного меньше. Для записей без исходных дорожек повторная транскрибация работает по смеси, как сейчас. Проверять нужно и в наушниках, и через колонки: во втором случае голос собеседника попадает в микрофонную дорожку.

Отклонено заранее: размечать источник у реплики смеси по тому, в каком источнике в это время был громче звук. Перебивания и одновременная речь в одном сегменте смеси так не разделяются, а это ровно тот случай, ради которого всё затевается.

Открытые вопросы до решения: нагрузка на CPU без GPU в живом режиме; поведение подавления эха на встроенных микрофонах ноутбуков; миграция схемы транскриптов под источник реплики (существующие встречи остаются без источника); как источник сочетается с метками диаризации в саммари.
