# speakrs на GPU через форк и прерываемая диаризация

Статус: часть 1 принята и сделана; часть 2 предлагается, в бэклоге.

## 1. Ускоритель и потоки speakrs через форк

speakrs — самый точный из наших движков диаризации, но на нашей сборке он считал только на CPU и упирался в одно ядро: у него нет режима DirectML (GPU только через CUDA и MIGraphX), а сессии ONNX Runtime для голосовых отпечатков жёстко ограничены одним потоком. 39-минутная запись не досчитывалась и за 7 минут. Родной CoreML-режим speakrs на macOS требует ~360 МБ заранее скомпилированных `.mlmodelc` и нового крейта `objc2-core-ml`.

Все наши ONNX-модели работают на одном ONNX Runtime: на Windows это сборка с DirectML, на macOS — с CoreML execution provider, и GigaAM уже ставит своим сессиям эти провайдеры с откатом на CPU. speakrs получает то же самое через форк `enrey/speakrs` (ветка `ru-meet`, подключён через `[patch.crates-io]` с закреплённым коммитом):

- фичи `directml` и `coreml-ep` ставят сессиям `ExecutionMode::Cpu` соответствующий провайдер перед CPU; ONNX Runtime сам оставляет на CPU то, что ускоритель не поддерживает;
- расчёт отпечатков в CPU-режиме получает до 8 потоков вместо одного (2 при ускорителе, на CPU остаются только остатки);
- шаблоны памяти выключаются при DirectML, который их не поддерживает.

Приложение включает `directml` на Windows и `coreml-ep` на macOS. Новых зависимостей и файлов моделей нет, правило «одна версия `ort`» соблюдено. На RTX 5060 Ti 39-минутная запись диаризуется за 153 с (15x реального времени). Вклад GPU и потоков по отдельности не измерен; CoreML-ветка на macOS ещё не проверена на железе.

Отклонено: родной CoreML-режим speakrs (+360 МБ моделей, новый крейт, только macOS) и CUDA на Windows (CUDA-сборка ONNX Runtime с CUDA runtime и cuDNN — гигабайт DLL, только NVIDIA, и вторая сборка ONNX Runtime рядом с DirectML-сборкой). Форк держим минимальным: правки помечены `ru-meet:` и пригодны к предложению в основной репозиторий; при обновлении speakrs ветка перебазируется на новый тег.

## 2. Диаризация в отдельном процессе (предлагается)

Движки диаризации — один блокирующий вызов без отмены. «Стоп» сейчас только ставит флаг, который проверяется после окончания расчёта: результат отбрасывается, но расчёт продолжает занимать CPU и GPU и держит очередь. Предлагается запускать диаризацию в отдельном процессе-помощнике (как `llama-helper` для встроенной модели саммари) и при остановке завершать его: «Стоп» освобождает ресурсы сразу, а падение движка не роняет приложение. Цена — передача аудио и результатов между процессами и ещё одна точка сборки и подписи бинарника. Решение не принято.
