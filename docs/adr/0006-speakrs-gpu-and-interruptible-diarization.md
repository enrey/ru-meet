# speakrs на GPU через форк и прерываемая диаризация

Статус: обе части приняты.

## 1. Ускоритель и потоки speakrs через форк

speakrs — самый точный из наших движков диаризации, но на нашей сборке он считал только на CPU и упирался в одно ядро: у него нет режима DirectML (GPU только через CUDA и MIGraphX), а сессии ONNX Runtime для голосовых отпечатков жёстко ограничены одним потоком. 39-минутная запись не досчитывалась и за 7 минут. Родной CoreML-режим speakrs на macOS требует ~360 МБ заранее скомпилированных `.mlmodelc` и нового крейта `objc2-core-ml`.

Все наши ONNX-модели работают на одном ONNX Runtime: на Windows это сборка с DirectML, на macOS — с CoreML execution provider, и GigaAM уже ставит своим сессиям эти провайдеры с откатом на CPU. speakrs получает то же самое через форк `enrey/speakrs` (ветка `ru-meet`, подключён через `[patch.crates-io]` с закреплённым коммитом):

- фичи `directml` и `coreml-ep` ставят сессиям `ExecutionMode::Cpu` соответствующий провайдер перед CPU; ONNX Runtime сам оставляет на CPU то, что ускоритель не поддерживает;
- расчёт отпечатков в CPU-режиме получает до 8 потоков вместо одного (2 при ускорителе, на CPU остаются только остатки);
- шаблоны памяти выключаются при DirectML, который их не поддерживает.

Приложение включает `directml` на Windows и `coreml-ep` на macOS. Новых зависимостей и файлов моделей нет, правило «одна версия `ort`» соблюдено. На RTX 5060 Ti 39-минутная запись диаризуется за 153 с (15x реального времени). Вклад GPU и потоков по отдельности не измерен; CoreML-ветка на macOS ещё не проверена на железе.

Отклонено: родной CoreML-режим speakrs (+360 МБ моделей, новый крейт, только macOS) и CUDA на Windows (CUDA-сборка ONNX Runtime с CUDA runtime и cuDNN — гигабайт DLL, только NVIDIA, и вторая сборка ONNX Runtime рядом с DirectML-сборкой). Форк держим минимальным: правки помечены `ru-meet:` и пригодны к предложению в основной репозиторий; при обновлении speakrs ветка перебазируется на новый тег.

## 2. Прерываемые фоновые вычисления

Движки диаризации выполняют блокирующий native-вызов без отмены. Флаг остановки отбрасывает результат, но оставляет CPU и GPU занятыми. Запись происходит в реальном времени и имеет безусловный приоритет: её старт не должен ждать окончания такого расчёта, который можно повторить.

Тяжёлая обработка сохранённого аудио — декодирование, VAD, повторное STT, диаризация — и встроенный summary выполняются в headless-режиме того же исполняемого файла. TTS использует тот же module управления дочерними процессами; сборка и кодирование озвучивания также вынесены в worker. Отдельный поставляемый бинарник для worker не нужен. Выбор провайдера и жизненный цикл STT остаются внутри `audio::transcription` согласно ADR-0002; live STT является частью записи.

Очередь выполняет одно задание. При старте ручной или автоматической записи module исполнения отправляет немедленное завершение всего дерева фонового процесса: Windows Job Object с kill-on-close, Unix process group. Захват не ждёт завершения или очистки worker. Передача большого запроса не удерживает lock управления процессом. После записи прерванная попытка повторяется на том же месте; настоящее падение сохраняет ошибку, освобождает очередь и требует ручного повтора в её конце.

Worker возвращает законченный результат; сохранение транскриптов, speaker turns и публикация готовых файлов остаются в основном приложении. Цена — повтор незавершённой попытки и загрузка модели заново. Завершённые предложения TTS остаются в кэше.

## 3. Минимальная нагрузка во время записи

На странице записи пользователь выбирает «Распознавать текст в реальном времени (выше нагрузка)». Переключатель по умолчанию выключен; значение фиксируется на всю сессию, включая автоматическую запись. Без живого STT приложение сохраняет аудио, а распознавание ставит в общую очередь после остановки. После успешного распознавания запускаются настроенные диаризация и summary. Ошибка распознавания не теряет эту последовательность при ручном повторе задания.

Записываемый смешанный звук передаётся на сохранение до VAD. Даже без живого текста один VAD продолжает определять речь: это требуется для остановки по тишине и отбрасывания пустых записей. В этом режиме VAD не накапливает сегменты для STT и модель распознавания не загружается.

Предварительное определение речи работает отдельно по микрофону и системному звуку только тогда, когда включён соответствующий запуск автозаписи и нет активной сессии записи. При записи эти предварительные VAD освобождаются; речь определяется единственным VAD основного потока. Индикаторы громкости используют RMS/peak и не требуют VAD. Обнаружение приложения звонка по владельцам микрофона также не требует VAD.

Все сессии Silero используют intra-op=1, inter-op=1 и отключённое активное ожидание потоков. Это ограничение относится к VAD; параметры GigaAM не меняются. Проверка на реальной речевой фикстуре должна сохранять аудио в обоих режимах, подтверждать определение речи и исключать выдачу STT-сегментов при выключенном живом распознавании.


## 4. Отложенное восстановление заданий

Ошибки атомарных заданий вместе с исходным запросом сохраняются в `failed-tasks.json` в каталоге данных приложения, определяемом `portable`. При запуске они появляются в очереди как отложенные повторы. Для ошибок summary, сохранённых старыми версиями в SQLite, исходный запрос строится из текущего транскрипта и настроек непосредственно перед повтором. Отсутствующий результат сам по себе не считается ошибкой: старые нетранскрибированные записи автоматически не обрабатываются.

Автоповторы допускаются не ранее чем через 10 минут после запуска приложения, только без записи и после завершения обычных заданий. Отложенные записи не занимают FIFO: новые запросы проходят раньше них, а новый запрос того же этапа и встречи заменяет отложенный повтор. Уже запущенный повтор использует общее прерываемое выполнение и освобождает ресурсы при старте записи.

За один запуск приложения выполняется не более одного автоповтора конкретной сохранённой ошибки. Счётчик сохраняется: после трёх неудачных автопопыток между запусками остаётся только ручной повтор, который сбрасывает счётчик. Успех или отмена удаляет сохранённую ошибку; задания удалённых встреч не запускаются. Кнопка «Запустить сейчас» позволяет пользователю явно отправить отложенный повтор в обычную очередь раньше срока.

При обнаружении ошибок читаются только небольшой журнал и ограниченный запрос метаданных summary; модели и записанное аудио для этого не загружаются. Запись сохраняет безусловный приоритет независимо от срока автоповтора.

## 5. Неустановленная модель саммаризации — необязательная возможность

Пользователь может вообще не устанавливать локальную модель summary. Если выбранной модели нет, она ещё скачивается или файл не прошёл проверку размера, автоматическая обработка после записи пропускает саммаризацию до создания задания и статуса PENDING. Ожидание установки, автоматическая загрузка и повторяющиеся ошибки в этом случае не создаются. Завершённые запись, STT и диаризация остаются сохранены.

Это же правило действует для восстановления старых ошибок при запуске и повторно проверяется перед отложенным автоповтором. Неисполнимые задания summary не удерживаются в очереди на случай будущей установки. Проверка читает только метаданные файла выбранной модели; чужая локальная модель не подставляется, облачные провайдеры не требуют наличия GGUF. Явный ручной запрос без установленной модели получает одну ошибку до создания задания.
